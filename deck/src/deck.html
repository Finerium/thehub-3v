A1 Compliance map, and the three answers in full

PRD 2.2, verbatim
KQ1

The Hub builds the foundation as an offline, versioned ingestion of every controlled document into typed packages keyed on the equipment tag (datasheet parameters, cause-and-effect rows, plot-plan and BOM facts, work orders, lessons), with document-to-document edges taken from the documents' own cross-references and a gate that fails the build on any dangling reference.

KQ2

Engineers ask in natural language and receive evidence packets: claims cited to approved revisions, numbers only from typed fields, procedures verbatim under hash, a deterministic confidence band, and an abstention with a named escalation when the corpus cannot answer; protective-function questions are classified before any model call.

KQ3

The Hub connects to operations through what operations already produce: work orders, proof-test results, setpoint ladders and the approval chain; it measures which failure knowledge has no lesson, drafts the missing lesson from evidence, routes it through the plant's Prepared/Reviewed/Approved chain, and specifies read-only connector contracts for EDMS, AIMS and the historian that a pilot activates without changing the product.

The compressions on slides 3 and 4 carry the same three labels; these are the sentences they compress.

A5 AI-tool usage, and how the work was validated

disclosed in full
In the build

The three repositories were built by an orchestrated run of Claude Code on Claude Fable 5.1, directed by the team lead. The model wrote code, documentation, this deck's source and the report from the PRD and the blueprint, provisioned platform resources through their CLIs, and ran the harness. It never saw a secret, never published a lesson, and never typed a number onto a surface: every figure here binds to the fixture, the bundle or the seeded database.

In the product

Every model role, the extractor, the composer, the drafter and the verifier, runs on one pinned provider and one model id through one gateway module, the only code path that calls a provider. The embedding role is a local, hash-pinned open-weights model. Safety intent is classified in deterministic code before any model call; the verifier never sees the question and never edits; the gates decide.

The validation loop
LayerWhat it does
Deterministic checksEvery change merges through a pull request with required checks: tests, lint, type check, secret scan, the banned-strings grep, the copy audit and the no-corpus-text check.
Fresh-context reviewRead-only verification fleets, separate from the threads that wrote the code, review each artefact and record a schema result on the pull request.
Independence, honestly statedOne provider and one model id, so verifier independence is prompt-and-question-blindness plus the deterministic gates, not a different model family. Stated here and on the Evaluation page rather than implied away.
Human acceptanceThe owner's acceptance of the report closes the loop. Only a human publishes, through G3.

Every generated artefact records the model id, the prompt version, the gateway configuration hash and the corpus version, so any answer, draft or evaluation run can be traced to what produced it.
